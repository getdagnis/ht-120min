# HT-120min fundraiser

The HT-120min campaign is a Buy Me a Coffee Shop fundraiser, not an interest poll. The approved artwork is in `plans/support-modal-whole-1.png` and `plans/support-modal-whole-2.png`. The modal uses the parchment, grass, badge, beer button, tank, and pump assets in `public/alus/`; the headline, introduction, product copy, supporter names, and beer total are HTML text. Its pump illustration holds each trophy/pump view before switching quickly and stops under reduced motion. Home and tournament pages show the modal on visits until it is dismissed; that dismissal suppresses it for the current browser session. A signed-in manager with a matched verified purchase no longer gets the automatic modal. A BMC thank-you return also suppresses it only for the current browser session while verification may still be pending. The dismissible fundraiser banner remains on Home and tournament pages regardless of modal eligibility; its action opens the modal on the current page. The modal closes from its close button or Escape. Visitors can view the fundraiser and purchase without an HT login. The campaign uses English copy on both site locales.

## Purchase and name flow

`POST /api/integrations/buymeacoffee` stays inside the consolidated Next.js API function. Configure a BMC webhook for `extra_purchase.created`, `extra_purchase.updated`, and `extra_purchase.refunded`, and set server-only `BMC_WEBHOOK_SECRET` in Vercel. The handler verifies `x-signature-sha256` against the untouched request body and ignores `live_mode: false` events. It attributes products by `data.extras[].id`, records EUR unit cents and quantities, and uses BMC payment ID plus item ID for idempotency. Refunds remove their beer and name contribution, including when they arrive before a create event. Unrelated donation events do not affect this fundraiser.

Each fundraiser button passes through `GET /api/app?route=fundraiser-checkout&item=...` in the consolidated API before redirecting to its published BMC Shop URL. It writes a private click row with product, timestamp, click ID and, when signed in, Hattrick manager ID. A signed, HttpOnly cookie carries the click ID for one hour; a failed click-statistics write does not block checkout. BMC redirects each product to `/supported?item=hfi|flags|120min|general`. First arrival receives a signed seven-day return cookie with its original timestamp and return key. If logged out, the page retains its URL in browser session storage and uses the existing CHPP return URL to resume after login. A signed-in claim records one private return per return key; refreshes reuse it. The webhook can match a pending return later. Matching prefers a same-manager click and a purchase within two minutes of the original return, then accepts a plausible same-product purchase within twenty minutes. The return record stores `click` or `timing` attribution for later diagnostics. Purchases made directly on BMC still count toward the beer total and can match a signed-in return by timing. A return alone never changes totals; the page uses neutral thank-you copy until a purchase match succeeds.

Migrations 169–171 are owner-marked applied and immutable. Prepared migration 172 adds private click records and idempotent return keys, and updates matching without changing the payment-ledger source of truth. Its tables and RPCs are service-role-only. The legacy `next_season_*` database names remain because migration 169 is applied; app-facing component names and URLs use `fundraiser`. The old vote API and UI are no longer used. `NEXT_PUBLIC_FUNDRAISER_STATUS` controls active, closed, and hidden display. Closed retains totals without purchase buttons; hidden removes the fundraiser.

## Activation and checks

The owner marked migrations 169–171 applied. Migration 172 is prepared and passed in a disposable PostgreSQL cluster; it has not been applied to Supabase. Apply 172 before deploying the API code that writes `fundraiser_clicks` and calls `claim_fundraiser_return`. Keep `APP_SESSION_SECRET`, `SUPABASE_SECRET_KEY`, and `BMC_WEBHOOK_SECRET` configured server-side. Then verify a signed test event and a real Shop purchase, including return, login recovery, supporter name, duplicate delivery, and refund behavior. Dashboard test events must not change totals. Local tests and disposable PostgreSQL checks do not prove live BMC, Supabase, or deployment behavior. Local development reads live totals but skips return claims and click writes.
