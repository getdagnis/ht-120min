# Shared predicted fixture ratings

`fixture_predicted_rating_shares` is the source of truth for one team's shared prediction in one arranged fixture. It has one row per fixture and participating club, with a distinct row ID so a pending refresh can update only the same share. `share_source` distinguishes explicit manual shares from automatic ones; pre-existing rows remain manual. The row stores seven converted sector values, formation, tactic, tactic skill, the optional coach modifier, optional Set Pieces skill, the linked Hattrick MatchID, and the last successful fetch time. It never stores lineup, player IDs, raw XML, or credentials.

The public tournament projection and browser fixture refresh read `fixture_predicted_rating_share_status`, a narrow view that exposes fixture/team/MatchID, sharing and opt-out status, and a recent order-check result for eligible upcoming fixtures. It exposes no prediction values. Each side without a visible prediction shows the shared confirmation, confirmed unset orders, unclear status, or not-yet-shared notice when auto-sharing is disabled. The base table is not publicly readable. A private, uncached `GET /api/app?route=fixture-ratings&tournamentId=...` returns both clubs' snapshots only to a signed-in manager whose stored credentials and live CHPP team list confirm ownership of an exact participating club. The values disappear at kickoff. On localhost only, the signed-in site admin identified by the configured `FORGE_SUPERADMIN_HT_ID` may see all upcoming shared snapshots when that variable is set to `8777402`; this exception does not apply in production. Share, Update, and Remove still require exact club ownership. Writes use the server's service role after session, fixture, and manager checks.

Share and Update fetch `matchorders` v3.1 with `actionType=view` for submitted positions, the taker, and the coach modifier, then `actionType=predictratings` for sector ratings and tactic skill. Only the exact -10/+10 coach-modifier endpoints are labeled and colored as Defensive 100%/Offensive 100%; neutral and intermediate settings remain unmarked. If there is a taker, `playerdetails` v3.2 adds the optional Set Pieces skill. The prediction request uses the saved match orders by omitting a lineup parameter. Sector values convert with `(raw + 3) / 4`. An unavailable optional player skill becomes `—`; a failed match-order request leaves any prior snapshot and timestamp intact.

## Automatic sharing

For local visibility testing, toggle `LOCAL_ADMIN_VIEW_ALL_SHARED_RATINGS` near the top of `src/server/api/_lib/fixture-ratings.ts`. It defaults to `true`; `false` uses normal participant visibility while retaining admin access elsewhere. Save the source file and reload the tournament page to fetch fresh private ratings; Next dev reloads the server module without a restart. The development, localhost and signed-in identity checks remain mandatory when enabled. This has no effect in production.

The Fixtures switch defaults to on for each team and manager in a tournament. `tournament_team_rating_preferences` stores only explicit preferences, without a season key, so opt-outs persist across seasons. GET/POST `/api/app?route=rating-sharing-preferences` uses signed-in sessions and live CHPP ownership verification. Tables and mutation RPCs are service-role-only; preferences do not affect who may read predictions.

Background fixture refresh creates an initial automatic share only for a current-season upcoming arranged fixture whose exact team's own `matches` response confirms `OrdersGiven=True`. Absent/false values do not trigger prediction reads, and another participant's fallback token cannot supply a positive orders check. Already-fetched match lists are reused. Fully reconciled fixtures normally skip the match-list read; automatic sharing reads the team's list only while it lacks an eligible share. A live token-holder club check still precedes prediction fetching. Initial creation is permitted by the stored default-on preference even when the refresh requester is not the owner; the response contains counts, never private values.

A team-row token is used for the orders check when available. A validated organizer addition without that token may use its recorded manager's saved profile credentials. This is an owner authorization lookup, not another participant's public-booking fallback. Missing or revoked owner authorization cannot create a share.

Once a valid share exists, background refresh neither reads orders for sharing nor fetches predictions again. An authenticated clicked Refresh fixtures updates existing manual and automatic shares in the actionable round after checking participation or tournament-management access. Updating an automatic share retains its automatic source. Explicit Share creates a manual share.

Switching off atomically deletes automatic shares for that team and cancels in-flight automatic claims; manual shares survive. Fixture Remove deletes its share and records suppression for the exact fixture/team/Hattrick MatchID, even if no row currently exists. Background refresh cannot recreate that match's removed share. Explicit Share clears suppression. Re-enabling the switch permits future automatic creation except for individually suppressed matches. Changed Hattrick MatchIDs have independent suppression.

`fixture_rating_automation` holds suppression, a two-minute claim, and a five-minute retry cooldown for pending/failed orders checks and prediction attempts. Concurrent refreshes claim the same side only once. CHPP requests run outside transactions, with a final atomic fixture/owner/preference/claim check before publishing. Preference writes and all Share/Update/Remove operations use the same tournament/team advisory lock. A removed row ID cannot be recreated by a clicked Update. A failed optional cache purge does not undo a successful write. Private client values reload when the public sharing-status key changes; switching off discards withdrawn local values immediately.

## Match-order notices

Migration `119_fixture_order_status.sql` carries an owner-added applied marker and requires 118; that marker is not independent live verification. It extends the existing private automation record and public status-only view. Confirmed `OrdersGiven=False` is recorded only after live ownership verification, under the pending claim and exact fixture/club identity. Missing credentials, failed requests and absent signals stay unknown; failed checks clear an earlier confirmed-false value. False observations expire after 15 minutes in both the view and client so they cannot become indefinite claims about current orders. Existing sharing confirmation wins; disabled auto-sharing without a manual share shows “has not shared their predicted ratings yet.” Individual Remove still suppresses auto-sharing and does not imply unset orders.

The existing five-minute retry cooldown remains; no order checks are added for disabled teams, individually suppressed fixtures, or existing shares. The public view checks season, kickoff, both real active clubs and the recorded Hattrick identities. Numeric predictions remain private. Migration 118 now has an owner-added applied marker, preserved unchanged; this is owner bookkeeping, not independent live verification. Apply 119 before deploying the expanded status projection. ### Public-loader compatibility incident (2026-10-13)

The expanded projection made order-status enrichment a hard dependency of every tournament page. On the connected application database, a read-only public query returned `42703: column fixture_predicted_rating_share_status.shared does not exist`, while the original three-column projection succeeded. This is live evidence that the connected view still lacks the expanded columns, regardless of reported migration application; no database changes were made during diagnosis. Both server and browser loaders now share `readFixtureRatingStatuses`, which retries the original status-only projection on undefined-column/schema-cache errors. Existing sharing notices remain available; missing order/preference data stays unclear. Permissions and other genuine failures are not swallowed, and the private shares table is never a fallback. Regression tests cover the legacy view, expanded view and denied reads. The server page logs the actual database error instead of replacing plain error objects with “Unknown error.”

The preference table in 118 also introduces a second PostgREST relationship between tournaments and teams. Live public Home reads failed with `PGRST201` until roster embeddings explicitly selected `teams!teams_tournament_id_fkey`. Home builder, legacy Home and open-tournament reads now name that direct roster relationship; do not use an unqualified `teams(...)` embedding from tournaments. The complete Home builder subsequently passed a live read-only run. The reported Forge chunk URL and `/forge` both returned HTTP 200 during diagnosis; that chunk failure was not reproduced and no bundler change was made.

Fixtures presents one “Auto-arrange my matches” control and one “Auto-share my predicted ratings” control per manager, irrespective of team count. Each control applies its value to every eligible owned team returned by its preference API. Per-team records and ownership checks remain intact for future manager settings. A mixed set displays on while any team is enabled, so switching off reliably requests all teams off. Saves use the existing per-team endpoints; successful writes update local state individually, partial failures remain visible and rating values reload after any successful write. No atomic bulk-save claim is made.

The same 118 relationship ambiguity applies in the inverse direction: dropdown participation, profile team lists, ownership reclaim, conflict checks and OAuth completion must embed `tournaments!teams_tournament_id_fkey` from teams. These callers now specify it; the dropdown's complete projection passed live read-only verification. Dropdown query failures are reported rather than converted into an empty participant list.

Each fixture side renders its prediction or status notice within the same ratings-grid column. Mixed prediction/notice fixtures no longer append a second full-width notice section; manual Share controls remain in that same column and existing mobile stacking is preserved.

## Specialty matchup hints

Paired predictions with known specialty snapshots color the pitch's specialty markers, including their counts. Technical wingers, forwards and inner midfielders use warning indicator 3 when the opponent has Head defenders or inner midfielders; those vulnerable Head markers also use indicator 3. Quick defensive/inner-midfield slots covering a Quick event initiator use green indicator 2, including possible cover elsewhere. Quick initiators without shown direct blocking use warning indicator 3. Tooltips distinguish direct and possible cover; green coverage is not a guarantee of blocking. Numeric matchup greens keep their existing accent color; indicator 2 applies only to specialty coverage. Quick midfielders are evaluated as both initiators and potential cover, with their own uncovered/partially covered threat taking precedence. Mixed groups split by indicator instead of coloring an entire count uniformly. Unknown specialty data or a missing opposing prediction leaves markers neutral. No Head-versus-Head cancellation is assumed.

These are conservative slot-based UI hints, not event probabilities or a current engine simulator. The role interactions follow [Hattrick's December 2017 developer explanation](https://devblog.hattrick.org/2017/12/a-new-match-engine-odyssey/); contemporary engine behavior has not been independently verified. No additional CHPP reads, stored fields or public prediction access are introduced.
